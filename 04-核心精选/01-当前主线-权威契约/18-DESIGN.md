# 设计说明

这份文件回答两个问题：为什么这么设计，以及踩过哪些坑。

---

## 一、四个基本决定

### 1. 状态用「事实」，不用「第几步」

「第 5 步」这种状态有两个致命缺陷：它不能回答"现在还能做什么"，也不能回答"还差什么"。

事实集合两个都能答：
- 能产出新事实的工具，就是能做的
- 目标里不在集合内的，就是还差的

所以 `world.py` 里没有 `step` 这个状态量。`run.json` 里的 `steps` 只是统计数字，没有任何逻辑依赖它。

连带的好处是不可达诊断能直接做出来：从目标往下走，走到没工具能产出的地方，就是断点，而且能报出完整依赖链。

### 2. 契约是数据，不是代码

条件写成 mini DSL 字符串（`branch == 'plane'`），实现写成模块引用（`mytools:cut_plane`）。

如果条件是 Python lambda：
- 别语言的 runner 解释不了
- 静态检查不了（写错了要跑到那一步才发现）
- diff 里看不出改了行为

现在是数据，`doctor` 能在 0.1 秒内把语法错、来源错、环、缺校验器全查出来。**这在分工场景下不是优化，是前提**——别人交上来的契约，你得能立刻验收。

### 3. 每个事实强制绑定校验器

工具返回 `ok=True` 只是"我认为我做了"。内核在工具返回后独立调用校验器，校验器从磁盘重算。

这条是硬约束：`contract.validate()` 发现某个事实有产出者但没有校验器，直接报错拒绝运行。

为什么必须这么硬：**工具自己说完成，和模型自己说测试通过，是同一类谎言。** 外部已有明确案例——编码 Agent 删了生产数据后仍报告"测试全部通过"。内核存在的意义，恰恰是不信自称。

### 4. 事实分两种量词：「一次达成」与「每实例达成一次」

前三个决定在第一版就定了，第四个是这一版补的，而且是被两个实验逼出来的。

初版里事实只有一个量词：在集合里就是成立。用它表达「6 个零件各清洗一遍」时，
内核跑完 1 件就把 `part_clean` 置位，随即判 `DONE` 并交付——**其余 5 件根本没做，报告却说成功**。
这是最危险的一类错：不是崩，是安静地骗人。

所以引入 `domain`：事实声明自己按实例展开，内部存成 `fact@实例`。随之而来四件事，缺一件都不成立：

| 机制 | 解决什么 |
|---|---|
| 三态 `satisfied()`：`True` / `False` / `None` | 清单还没产生时，「做完了吗」既不能答是也不能答否。压成布尔无论压哪边都会造出一个专门的假象 |
| `ready()` 与 `satisfied()` 分离 | 前者答「下游能不能开工」，后者答「整件事做完了吗」。一件被放弃，前置仍可放行其余件，但目标绝不判成功 |
| 实例作用域 `values["@实例"]` | 6 件都写 `part_path`，扁平命名空间下最后只剩 1 个——静默丢数据，比报错难查 |
| `abandoned` + 放弃级联 | 单件失败只弃一件；不沿依赖链传播，下游会一直等一个永远不会来的实例，最后报「走不通」，把排查方向带偏 |

关键选择：**域挂在事实上，不挂在工具上。** 同一事实可以有多个产出者
（`segment_semantic` / `cut_plane` 都产 `parts_available`）；域若写在工具上，两个产出者能写出
两种量词，「算不算达成」就没有唯一答案了。挂事实上，规划器只需查一处。

## 二、六条硬约束（本轮又补了三条）

全部在 `loop.py`。缺一条这个系统就会开始骗人。

| 约束 | 具体做法 | 少了会怎样 |
|---|---|---|
| 预算 | 步数 + 墙钟双上限 | 出错时烧一整天 |
| 防环 | 工具名 + **已解析参数** + **实例** 的哈希作为指纹 | 只判工具名不够：换参数重跑合法；6 件用同工具同参数时第 2 件会被误判为绕圈 |
| 不自证 | 必须过独立校验器 | 工具可以自己宣布成功 |
| 失败是数据 | 每个工具预先声明 `on_fail` | 现场临时拍脑袋，且不可审计 |
| 准入失败 ≠ 执行失败 | `admission` 标记，结局分 REJECTED / FAILED | 把"你的数据不合格"写成"系统坏了" |
| 留痕 | 记「为什么选它」+「为什么没选别的」 | 那就只是执行日志，不是决策日志 |

本轮又补了三条，同样在 `loop.py` / `planner.py`：

| 新增 | 具体做法 | 少了会怎样 |
|---|---|---|
| 路线优先 | 目标有多个产出者时，先按 `priority` 定路线，再沿路线找第一步 | 纯贪心偏向当场能跑的那条；人给了割线也会自作主张去认语义 |
| 放弃不等于成功 | `skip_instance` 记进 `abandoned`，目标判定仍走 `satisfied` | 少做一件还报成功，与初版的假成功同类 |
| 预算建议 | 耗尽时用 `preview(world=…)` 从当前状态符号推演剩余步数 | 只说「步数用满」对人没用；N 件 × M 环节的账人不会自己数 |

留痕这条需要展开说。只记"做了什么"的日志，事后只能回答"它做了什么"；记了"考虑过什么"的日志，才能回答"它是不是选错了"。后者才是复盘需要的。

报告里那段「同时可用但没被选中的」就是这么来的。

## 三、LLM 放在哪

**主规划器不接 LLM。** 理由不是保守，是这条链确定性可解：

- 通常 10 来个节点、2 个分支、1 个回退
- 目标回归一遍就能得出唯一最优下一步
- 模型来选不会引入能力，只会引入不确定性

而且它不可审计：一次幻觉就足以让链跑到错的工具上，事后很难查——因为"当时为什么选它"没有可复现的依据。

LLM 真正适合的是三处窄接口：

| 位置 | 做什么 | 猜的部分怎么处理 |
|---|---|---|
| 任务单解析 | 一句人话 → 结构化任务单 | 只做路径抽取，猜的标 `assumed` 并进报告 |
| 失败翻译 | 把 reason_code 翻成人话 + 给下一步建议 | 只写文字，不改判定 |
| 报告叙事 | 写报告的说明段 | 数字由代码填，模型不碰 |

三处都留了位置，都可关。`llm.py` 的 `LLMPlanner` 是接口占位，调用会抛错——
留它是为了让"想过要不要接、为什么没接"这件事留在代码里，而不是散在聊天记录里。

如果确实要试，正确做法不是在 planner 里加 API 调用，而是在内核外面写一个**候选生成器**：
它提供候选工具顺序，仍由内核做 `requires + guard` 校验和后果评估。这样模型错了也只是"候选差"，不会"后果错"。

## 四、踩到并修掉的坑

都是"看起来对、其实在骗人"那类。记在这里，因为下一个人一定会踩。
「诊断误判」到「其他几个小的」是第一版踩的；下面两个实验和末尾「多实例改造又踩的七条」
是本轮补的——后者更隐蔽，因为系统不崩，只是安静地少做几件事。

### 本轮新增：两个实验先证明了缺陷，再动手改

改代码之前先跑了两个实验，没有凭感觉重构：

1. **假成功**：造 6 个零件都要 build 的场景，旧内核跑 1 次 `build_part` 就报 `DONE` 并导出。
2. **静默丢数据**：6 个零件都写 `part_path`，扁平 `values` 里最后只剩 `hair.stl`，前 5 个路径消失且无任何告警。

这两条决定了后面所有的设计，也进了验收（T17 / T24）。**先复现再修**，避免"改了一通其实没打到点子上"。

### 诊断时用实时状态检查 `requires`，每条正常路径都误判不可达

`diagnose()` 里调 `tool.guard(world, ...)`，而 guard 会检查 `requires` 的事实是否成立。
但诊断时前置本来就还没产出——于是所有依赖链都在第一层断掉，报"没有工具能做"。

修法：给 `guard` 加 `check_requires=False`，诊断时前置可达性由递归自己判断，只查任务单字段和条件。

与此配套：条件表达式在诊断期可能引用还没值的量（比如 `mode` 要等 `route` 跑完）。
静态无法判定时按"可能可行"处理，不判死。真正的语法错由 `doctor` 抓。

### 规划器没跳过「产出已满足」的工具，`route` 被反复选中

`planner.next()` 遍历候选时漏了一句 `if t.produces in world.facts: continue`。
于是它反复挑同一个工具，靠主循环的防环去兜底。

这是把**逻辑错**当**运行时异常**处理，必然空转。防环是最后一道保险，不该是第一道。

### `\r\n` 让守恒式永远对不平

工具用 `open(path, encoding="utf-8").read()`，Windows 上会把 `\r\n` 转成 `\n`；
校验器如果用了不同口径，两边算出的字符数会差几十（1507 vs 1460）。

修法：两侧一律按字节读（`open(path, "rb").read().decode("utf-8")`）。
**字节级一致是守恒校验的前提，不是讲究。**

顺带还修了另一个同源问题：分块正则 `[^\n]+` 会把 `\r` 当成行内容，
于是 `\r\n\r\n` 被看成"一个只含 \r 的行"，整篇被并成一块。这个错很安静，只在块数上露馅。

### 校验器只读本次 `values`，变成自评

校验器本该判"世界在这一点是否成立"，但它只读 `payload["values"]`（本次工具返回值）。
结果 `check_blocks` 找不到上游写的 `blocks_path`，报"工具没有给出"。

修法：校验器应该读 `world.values + values`（后者覆盖前者）。
只看本次返回值，就变成让工具自己给答案对答案了。

### 回退目标的条件和被回退工具互斥，回退是空的

`cut_fixed` 的条件是 `mode == 'fixed'`，回退目标写了 `cut_adaptive`，
而后者要求 `mode == 'adaptive'`。这条回退永远走不通。

在纸面上看不出来，只有真出故障那天才会发现备选没用。
现在 `doctor` 会报警告：回退目标带不同条件时提示"可能互斥，请确认"。

### Python 进程内实现超时杀不掉

`python` 类型用线程 + `join(timeout)`，超时只能放弃等待并标记，
线程仍在后台跑。`cmd` 类型才有真超时。

这一点写进了错误信息（"进程内调用无法强杀，可能仍在后台运行"），
不假装成功杀掉——重工具应该用 `cmd`。

### 其他几个小的

- **参数引用混了两种语法**：`$input.model` 是点号分层，`$run_dir/x` 是拼路径。
  一开始混在一起，`$run_dir/blocks.json` 被解析成"来源 run_dir/blocks"，doctor 报一堆假错。
- **桩检测被 docstring 干扰**：按行过滤会把多行 docstring 的正文当成代码，永远判不出桩。
  改用语法树看函数体是不是只剩一句抛错。
- **步数混了"本次"和"累计"**：续跑时把上一次的决策也算进来，于是"一个动作都没做"被报成"做了 1 个"。
  现在分开记 `steps`（本次）和 `decisions_total`（累计），预算按累计算。
- **`NOT_IMPLEMENTED` 被当成准入拒收**：实现没写被判成"你的数据不合格"，方向完全错了。
  现在准入判定排除这个码，结局是 `UNDECIDABLE`。
- **工具失败后结局判成"缺输入"**：已经干过且坏了，之后无路可走，应该是 FAILED 不是 UNDECIDABLE。
  混起来会把"工具骗人被拦住"写成"你的输入不够"。

### 多实例改造又踩的七条

1. **`values_global` 通道是断的（本轮文档核对时才发现）。**
   `loop._commit` 读 `res["values_global"]` 往全局合并，`split3d_impl.py` 的注释也教人用它写
   `clean_dir` 给下游取，但 `executor._normalize` 构造返回字典时**根本没带这个键**——
   那段合并是死代码。表现最阴：下游一次性工具用 `$value.clean_dir` 读不到，报的是
   「参数取不到」，看起来像缺输入，其实是值在适配层被丢了。
   修法：在 `_normalize` 透传并做类型保护（写成非 dict 就当没给，别把内核带崩）。
   **T24 专门为它立的碑，还做了负向实验**：撤掉透传，T24 立刻变 `UNDECIDABLE / NEED_INPUT`（4 步）。
   这条教训是通用的：**每一条"内核承诺工具能用"的通道，都要有一条端到端验收从工具写到下游读。**

2. **实例清单未知时被静态诊断误判 `UNREACHABLE`。**
   清单是运行时才产生的，静态推演却按实时世界检查，于是 `plan demo --goal book` 报不可达。
   修法：`diagnose(loose=True)` 只查任务单字段和条件；预览用 `PENDING = "<待定>"` 占位，
   并在那一行标明「会跑 N 次」。运行时则只在 `requires` 全部已完成后才检查清单是否兑现。

3. **单件失败导致整批中止。**
   `clean_chapter` 仍用 `abort`，12 章里第 5 章坏了，前 4 章白跑、后 7 章不做。
   修法：`on_fail=skip_instance` + `abandoned` + 沿依赖链级联放弃。最终 11 件做完、1 件入账放弃、
   三个环节都记着 `ch05`，结局老实判非成功。

4. **贪心规划器把"人给了割线"让位给了算法偏好。**
   `cut_plane` 要先降面、读割线、定分支；`segment_semantic` 当场能跑。纯贪心永远选后者。
   `priority` 设反了一次也没用——问题不在排序，在「只选当前能跑的一步」。
   修法：`_prefer()` 先按 priority 定路线，再 `_first_action()` 沿路线往回找第一个可执行动作。

5. **读写两侧口径不一致，同一个坑踩了两次。**
   第一版统一了读侧按字节读；本轮多章工具写侧用了文本写（`\n → \r\n`），
   工具算 118 字符、校验器从盘上读到 121。补 `_write_text()` 按字节写，读写成对。

6. **JSON → bash heredoc → Python 源码三层转义把测试代码写坏了。**
   注入的 `\n\n\n` 被写成真实换行，`liar_tools.py` 直接语法错。改用 `chr(10)*2` 绕开。
   之后第一次撒谎又没生效：清洗后的文本没有连续空行，`replace` 什么也没做；
   改成等长替换 `"第" -> "递"`，字符数完全正确、只有逐字重算能发现，才真正测到校验器。

7. **报告在多件场景下不可读。**
   「未选中」把同一工具列 12 次、独立校验刷 35 行「通过」、没有件账、段号重复、
   放弃的 `ch05` 出现三行、产物清单里 12 件挤成一片。
   修法：新增按实例统计矩阵（✓ / ✗ / 弃 / ·）、备选去重计数、独立校验按工具聚合、
   产物超 16 个按目录聚合、动态段号、放弃按实例合并一行。
   **"跑了 36 步"说明不了什么，"12 件里 11 件做完"才是结论。**

顺带修的脆断言：T2 原来写死了 8 步的完整顺序，路线优先让无依赖的 `route` / `ingest` 换了先后
——两种顺序都合法。改成依赖约束断言，不再假设没依赖的工具谁先谁后。

### 归属判据：能被函数判定的，别写进技能

`19-分件技能/skills/part-semantics/SKILL.md` 里有一条「调用前自查（契约漏项）」：
说 `segment_semantic` 的 `requires` 只写了 `input_ok`，但 `params` 用了 `$value.lod_path`，
实际依赖 `lod_ready`，于是要求「技能侧调用前自己确认 `lod_ready` 已成立」。

缺陷是真的，我实测坐实了：`resolve_params` 在只有 `input_ok` 的世界里直接抛
`MissingParam → 世界值里没有 lod_path`。而整链预览却显示
`probe_import → prep_lod → segment_semantic`，看不出问题——因为 `cut_plane` 那条路线
priority 更高，规划器先沿它排了 `prep_lod`，值**碰巧**先写好了。
把 priority 改一改、或者单独跑这一步，立刻变成 `MISSING_PARAM`（步骤级 reason），
排查方向容易被带成「环境/分割器没装好」。

但把修复责任交给技能是错的。按这轮定下的判据：
**「上游事实是否在依赖链上」能被静态判定，属于内核，不属于技能。**
靠提示词自觉去补一个确定性检查，正是「把能判定的事交给不可靠执行者」。

还挖出一个更根上的漏洞：`validate()` 的 `written` 集合把「params 里被读到的
`$value.K`」也算作「有人会写」，等于**有人读就算有人写**——
所以 `domain.from` 检查会对漏声明的清单放行，隐式依赖也查不出来。

修法三步，都在内核侧：

1. `written` 只认 `writes`，不再把引用算作产出。
2. `validate()` 新增静态规则：`$value.K` 必须有人声明写入，且写入者产出的事实
   必须在本工具 `requires` 的传递闭包内；否则直接判死。
3. 修契约：`probe_import` 补 `writes`（`model_path` 等四个键），
   `segment_semantic.requires` 补 `lod_ready`。

**T25 立的碑**，并做负向实验：屏蔽这两条静态错误后 T25 立刻失败。

这件事同时确认了另一半边界：契约里本来就没有「部位正确性」这个事实或校验器。
`part_verified` 只查水密、自交、体积、壁厚，一块从膝盖切下来的件同样全过。
**校验器能证明它是零件，不能证明它是那个部位**——这个缺口不会因工具补齐而消失，
只能靠人确认。把它写成校验器，得到的就是 L8 那条已被证伪的路。

### 复核后的两处纠正：判据不能整段套用，检查器不能只看 id

技能侧把这条整改接了，但指出**「删掉整段」删过头**，我核对后认同。两件事要分开：

**1. 静态检查有通道边界，判据要按「片段」用。**
`contract.py` 的隐式依赖规则只对 `$value.*` 生效（`if head != "value": continue`）。
`_PARAM_SRC` 里 `input` / `task` / `env` 等 9 类来源中，运行时字段是否真的传了
**无法静态保证**——契约能写 `needs_fields: ["inputs.seam"]`，不能保证用户没漏 `--input seam=`。
所以 `MISSING_PARAM` 仍会真实发生，而「这个码该读成什么」没有函数能判，属技能。
同一段技能里因此是三段归属：`$value` 上游就绪 → 内核；错误码语义 → 技能；
历史注 → 技能。**删掉自查纪律 ≠ 删掉整段。**

实测口径也校准了：漏传 `$input.model` 给的是 **0 步 `UNDECIDABLE / NEED_INPUT`**，
reasons 会点名缺哪个字段，并不是「内核把它误报成环境坏了」；但步骤级 reason 仍是
`MISSING_PARAM`，且同一顶层码同时覆盖「用户没传」和「上游 `$value` 没写」。
技能该写的是「先分是任务单没给还是上游没写」，不是指责内核报错。

一句话记法，双向适用：
**技能里每出现一条「你先自己检查 X」，都要问 X 能不能被函数判定；
能判的搬回内核，判不了的才留在技能。**

**2. 同一种病的另一层：只看 id 存在，看不出内容漂移。**
技能侧 `check_terms.py` 前四类检查只验「id 在不在」，所以我 21:35 一改
`segment_semantic.requires`，技能文档就进入静默漂移而自检仍绿。
它补了第 5 类「契约快照」逐行对账 `produces / requires / priority`，第一次运行
就抓出真 bug——不是伪造样本。

**我这边有完全一样的洞，而且正在发生**：`PACK-SPEC.md` 3.11 的示例还写着
`segment_semantic.requires: ["input_ok"]`，与 3.2 的正确示例和 manifest 互相矛盾。
`doctor` 只查 manifest 内部自洽，不查「接口书里抄的契约片段」；
`accept.py` 也没有任何一条管这件事。

修法与技能侧对称，但落在内核侧：

- 把 3.11 的示例改成带 `CONTRACT-SNAPSHOT` 标记的 JSON 数组（契约副本），并同步为正确值。
- 3.2 那个 `// 错：` 是**故意写错的反例**，不带标记，不参与对账——检查器必须能区分。
- **T26** 解析锚点块，逐字段对账 `produces / requires / priority`；标记消失也报错，
  不允许「因为找不到快照就静默 PASS」。
- 双层负向实验：把检查器屏蔽成永远返回一致 → T26 失败；真把磁盘上的示例改回旧值 →
  报 `文档 ['input_ok']，契约 ['input_ok','lod_ready']`，与技能侧抓到的那条逐字同形。

两层的教训是同一句：**「有人在读」不等于「有人在写」，「id 在」不等于「内容对得上」。**
前者是契约层的洞，后者是文档层的洞；两者都不会报错，只会静默失效。

## 五、已知局限

这些是这一版**没解决**的，不是遗漏：

1. **只支持「一个目标可以从一个根展开」的形态。**
   当前是反向展开 + 路线优先。如果一条链需要"先做 A 才能知道 B 该怎么做"的多轮迭代，
   或者多个目标互相冲突（资源争抢），这套推不动。
   **>2 件的连接图正是这类问题**：选哪两件之间加销、销的数量怎么分配、装配顺序怎么排，是组合优化，
   不是反向展开能解的。契约位已经留好（`contacts_found` 产出 `pair_ids`，后续逐对 `build_joint` / `verify_joint`），
   但「哪几对才够把整体连成一棵树、销位怎么全局分配不打架」仍要引入
   "候选方案生成 + 评估打分"这一层，而不是继续加契约。

2. **没有并行。** 工具调用的 DAG 里本来有可并行的分支（比如两个独立件的清理），
   现在串行跑。加上去不难，但要先把「并行失败怎么归因」想清楚，否则错误信息会变得没法读。

3. **续跑共享预算。** 预算按累计步数算，续跑不会重置。这是有意的（防止靠续跑绕过上限），
   但如果一次运行被外部中断多次，可能提前耗尽。

4. **同一个 `run_dir` 不支持并发。** 没有文件锁，两个进程写同一个目录会互相污染。

5. **条件 DSL 不支持算术。** `a - b > 3` 写不了。目前够用，因为算术应该在工具里做完再写进 values，
   而不是让编排层做数值计算。

6. **`python` 实现超时不可强杀**（见上）。

7. **没有工具级别的权限隔离。** 工具能读写整个磁盘。当前假设包是可信任的；
   如果以后要跑第三方包，得加沙箱。

## 六、如果要继续往下做

按性价比排：

1. **把 `split3d` 的桩填掉**（这是「另一个人」的活）。契约已重写成 `0.2.0` 的语义分件形状，
   不再是「切一刀成 2 件」。填的顺序按依赖链：
   `probe_import → prep_lod → segment_semantic / seam_ingest → route_branch → cut_plane →`
   `clean_part → verify_part → find_contacts → build_joint → verify_joint → export_part → assemble_check`。
   按实例工具一次只做一件、实例参数从 `inp["params"]` 取、全局值走 `values_global`——
   照 `packs/demo/` 的多章样板比形状。每填一个就 `doctor` + `plan` 跑一遍，不要等全填完再联调。

2. **语义分件**（`segment_semantic`）。契约位置留好了，两条路线（有显卡走 PartField / SAMPart3D / HoloPart，
   无显卡走人工关键点 + 测地线或热扩散）写在 `split3d_impl.py` 的注释里。
   `part_ids` 必须是带语义的字符串（`head` / `arm_l` / `bag` / `shoe_r` / `hair`…），
   不能编成 `piece_A`。这是整件事真正的缺口。

3. **多件连接图**。这一步要改规划模型，不只是加工具。见第五节第 1 条。

4. **失败翻译接 LLM**。这是三处窄接口里最安全的一处：只影响文字，不影响判定。
   适合用来验证"LLM 在这套架构里到底该放在哪"。

5. **装配验证从「几何可成立」升级到物理仿真**。当前 `assemble_check` 只核对对齐、不穿模；
   真正「站得住」需要仿真或实测（SNAP3D 那条有连接 + 仿真才 95% 稳定的结论就是依据）。

验收现状：`python accept.py` → **26/26**。T17~T24 围绕多实例语义与值域通道（其中 T24 是文档核对时发现 `values_global` 断链后补的）；T25 锁静态隐式依赖，T26 锁接口书契约快照与 manifest 对账（见 §四末）。数字以 `accept.py` 的 `CASES`（T1~T26）为准。
