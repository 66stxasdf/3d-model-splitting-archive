## 二、仔细推敲：七处必须说清的地方

### 1. 「基础都没做」只对了一半

| 层 | 实测现状 |
|---|---|
| 语义标签（哪块是头） | **零**。`segment_semantic` 是桩，真跑 1 步 `UNDECIDABLE / NOT_IMPLEMENTED` |
| 几何执行（布尔、接触面、销孔、剖面图） | **已有**：16 仓 L20，9/9 回归 |
| 参数化建模 + 分件基准 + 可分离性 | **已有**：01 仓 `build.py` / `separability.py`，BOLT01 11 件、MK02 37 件 |
| 调度、独立校验、拒收、留痕 | **已有**：18 仓 26/26，19 仓技能 PASS |
| 文献整理 | **已有**：19 篇 + 分类索引 + 179 行总表 + 233 行综述 + 222 行导师汇报 |

真正缺的是「语义标签从哪来」和「表面片补成实体」两环，不是地基。

### 2. 论文整理不是待办，成果是「没接上」

`论文爬取/` 于 2026-10-30 已完成：19 篇分 5 类、六根支柱、术语解析、「按流水线取用」速查表。
但 18 仓 `split3d_impl.py` 注释引用的 PartField / SAMPart3D / HoloPart，
与文献总表的 PartField / Segment Any Mesh / MeshSeg / Chopper / Interactive Partitioning
**只有一篇重合，各说各话**。这是前几轮反复抓到的同一种病：不是没做，是两层不对接、静默漂移。

### 3. 「让 Agent 看答案自己改」不会增强能力

- 内核是确定性的：契约是数据、主规划器不接 LLM、工具是固定函数。**没有权重被更新**；在没有错误记忆层之前，同一个输入会重复触发同一个错——这不等于「永远学不会避开」，见 §3.1。
- 「自己检查自己」同时撞两条：①「这是头吗」没有函数能判；② 项目铁律是不信自称、必须独立从磁盘重算。
- 差异能被算出来，但「差异 → 该怎么改」没有函数。硬做就退回 L8 那条已被证伪的路（93.6% 规则标签能被纯位置复述）。

**正确用法**：已分好的模型不当「反馈」，当**标尺**和**样本**。三个循环里，只有「验收」和「训练/沉淀」成立，「自动纠错」不成立。

#### 3.1 「学习」要按含义分开判（2026-11-11 澄清，修正上文口径）

用户定义的学习不是「每次跑完改自己」，而是**记下错误 → 再遇到同一个时能认出 → 不再重犯**。按这个定义，它是成立的、应该做的，且与确定性内核不冲突：记忆是数据、命中是查表、规避是规划器先验，成败仍由独立校验器从磁盘重算。上文「跑 100 次还是同一个错」只描述**尚无错误记忆层**的现状，不是能力上限。

- **现状**：`runs/*/run.json` / `events.jsonl` 已记下每次失败的 `reason_code`、工具、已解析参数、实例、失败时的事实集合；`on_fail` 是作者预写的经验，但只覆盖预想到的错；`state.json` 只存世界状态（续跑用），不存「上次栽在哪」。缺的是跨 run 索引与下次启动时的命中注入——不是从零做。
- **三个必须先想清的点**：
  1. **同码不同病**：`DESIGN.md` §四已实证，同一个顶层 `MISSING_PARAM` 同时覆盖「用户没传 `$input.model`」与「上游 `$value` 没写」。只按错误码建指纹会把两种病当一种，下次「改正」就是误改；指纹必须带病因字段。
  2. **「及时改正」分三档**：① 提前警示 / 拒收（纯确定性，最安全，先只做这个）；② 把上次失败变成路线先验、优先走备选（有风险：`DESIGN.md` 已踩过「贪心把人给的割线让位给算法偏好」，历史经验不得盖过人给的 `priority`）；③ 自动改参数 / 改代码（用户明确不要，且「差异 → 怎么改」无函数，见上文）。
  3. **经验会过期、会变成新的自称**：装了 torch、换了契约版本或模型后，旧条目命中即是新 bug。每条经验须带适用条件（契约版本 / env / 输入指纹），并允许被独立校验器证伪作废。
- **归属按片段判**：写库 / 命中 / 注入 → 工具（函数可判成败）；「算不算同一个错」「这条该不该采信或作废」→ 技能 / 人；「差异 → 怎么改」→ 两边都不写。
- **流程位置（经 §3.2 重排后修正）**：不再设独立的「阶段 1.5」。基础设施类错误（缺参数、桩未实现、预算耗尽、清单撒谎）由 `reason_code` + 独立校验器判定，**不依赖真值集**，可立即作为阶段 1 的并行项做；只有语义质量类错误（灌错标签、边界偏差）才必须等阶段 1 评估器与阶段 2 真实推理之后纳入。错误记忆是贯穿机制，不是一次性阶段。
- **边界**：能让 `MISSING_PARAM` / `NOT_IMPLEMENTED` / `BUDGET_EXHAUSTED` / 灌错标签这类**可判定的错**不再重复；**不能提高语义正确率**——「头认错了」没有函数能判，仍要靠真值比对 + 人确认边界。

#### 3.2 顺序推敲：本轮重排改了什么（2026-11-11 第二次整理）

上一版把错误记忆单列为「阶段 1.5，排在阶段 1 之后」，理由是「依赖真值集提供『什么算错』的口径」。复核后**这个理由说过头了**，本轮改掉：

1. **依赖只覆盖一半错误**。`MISSING_PARAM` / `NOT_IMPLEMENTED` / `BUDGET_EXHAUSTED` / 清单撒谎由 `reason_code` 与独立校验器判定，不需要真值集；只有灌错标签、边界偏差这类语义质量错误才要评估器。把整件事押在阶段 1 之后，等于把不必等的部分一起推迟。
2. **它不是阶段，是机制**。「留痕」「独立重算」本来就在 §四 贯穿约束里；错误记忆同属这一类，要随每阶段新出现的错误类型持续生长。单列阶段会让它看起来像一次性交付物。
3. **现在恰是做机制最便宜的窗口**。`split3d` 全是桩，能采集的错误几乎只有 `NOT_IMPLEMENTED` / `NEED_INPUT`，样本单一、结构稳定，正好用负向实验把「第二次命中」和「同码不同病因不得误命中」测对；等阶段 2/3 出现大量真实失败时机制已稳。
4. **阶段 0 已关闭**。上一轮已按「工程可用」拍板并获授权不再回头确认，不再是待执行阶段；流程从阶段 1 起算。
5. **阶段 2 的可行性探针前置**。原文把「装 torch + 取权重」放在阶段 2 第 1 项，而停手条件是「拿不到就转无 GPU 路线」——做完阶段 1 才撞墙是事后发现。改为阶段 1 先做低成本探针（权重可获取性、8GB 是否够、无 GPU 备选路线选定），安装仍留阶段 2。
6. **阶段 3 连接层措辞收窄**。§二.7 已实证 `find_contact` 判据与 `gap=0.15mm` 冲突、且只在人工割线的 2 件上验过 9/9。不能写「适配」，要写「先替换/放宽接触判据并在 N 件语义分件上重跑回归」；输入是人工合成整体（§二.6 域偏差），跨分布按 `UNKNOWN`。
7. **验证链要分只读与写入**。`accept.py` 会 `shutil.rmtree` 重建 `runs_accept/*`，而 20 仓 `build.py` 正是读这些 `events.jsonl` 生成 HTML 并复制桌面副本。只改口径文档时无谓重跑会造成桌面/主副本 sha256 漂移；故本轮只用只读三件套对账，`accept.py` 仅在契约或代码真改动后重跑并同步重建工作台。

**重排后的顺序**：阶段 1（标尺 A 线 + 错误记忆 B 线并行，零装机）→ 阶段 2（开源基线）→ 阶段 3（实体化/连接/装配）→ 阶段 4（可选自研）。每阶段统一按「产出 / 可复算验收 / 负向实验 / 停手条件」四栏判，没过不进下一阶段。

### 4. 「语义分割」窄化了需求

四阶段：预处理/修复 → 语义识别 → 实体化 + 分割优化（禁切） → 连接 + 装配验证。
SNAP3D 实测：**只用现成语义分件 → 重力落下测试 0% 稳定；加连接 + 仿真 → 95%**。
11-10 的 HANDOFF 已定「先补连接层，再上语义分件」。只盯第 2 格，会做出标签很准但拼不起来的东西。

### 5. 「按论文自己编写一套」的五个缺点

1. 文献总表第 83 行原话：PartField「**不用你训练**；前馈 ~10s 出特征场 → 聚类即部件」。它是权重，不是照论文能写出来的算法。
2. **本机实测无 `torch`**（有 RTX 5060 Laptop / 8GB，但没装深度学习栈）。跑推理要先装环境；从零训练还需要大规模逐面片标注数据，8GB 不够。
3. 论文指标不能当验收：mIoU 79.18% 是 PartNeXt 上的，跨分布 50.22；mIoU 量标签对不对，不量水密/壁厚/能不能放销。
4. 没有标尺时，读完论文也无法判断哪个方法适合自己的模型，只能按论文数字挑——最容易自欺。
5. 学位创新（有导师、阶段 1 汇报）与工程可用是两条路径。创新点应来自「开源基线在我的数据上暴露的某一类可命名缺陷」，不是从零造分割器。

### 6. 真值集里两个隐蔽的坑（本轮新抓）

实测 `01-ColorPartsKit`：把 STL 合并成「整体 + 逐面片标签」**可行**（BOLT01 19,249 面 / 11 类标签一一对应，MK02 48,520 面 / 37 类）。但：

- **不是水密**：BOLT01 只有 6/11 水密、MK02 只有 9/37，焊接顶点后无改善，是真开放。
  → 当**语义标签真值**合格；当**可打印几何真值**（体积/壁厚/封闭性）不合格，需先修复或改用 STEP。
- **没有对应的「未分件光滑整体」**：这些是设计出来的分件，件间 `gap = 0.15mm`。整体要人工合成 → 合成分布 ≠ 真实 AIGC 网格分布，**存在域偏差**。按既定规则，跨分布时整个分区按 `UNKNOWN` 处理，不许拿数字硬证可用。
- **真值不是唯一正确答案**：缝线是设计师定的，换个人分可能不同。指标必须叫「与这套设计的一致度」，不能叫「语义正确率」，否则重蹈 L8 拿代理指标冒充真值。

### 7. 「连接层已做」说满了，要收窄

16 仓 `l20_contact.find_contact` 的判据是「**顶点重合 + 面法向相反**」，前提是两件从同一整体切开、切面顶点严格重合；而 01 仓件间有 0.15mm gap，**不满足前提**。且 L20 是在人工割线切出的两件上验证的，没有在 N 件语义分件上验证过。
准确说法：**能力原型已做、集成未做**。复用时要么放宽接触判据，要么改成基于距离/投影的检测。

### 8. 「按类型调用拆分技能」：路由的形状对，拍板的方式错（2026-11-11）

用户想法：Agent 的基本能力是**任务理解**——给它一个整体 3D 模型，它判断该怎么拆；
手办类走一个拆分技能，机器人类走另一个；Agent 要会的是「认出手办还是机器人，调用对应技能」。

**对的部分**：
- 「Agent 不亲自拆、只负责调度」与现状一致：内核零领域知识，13 个实现全是插槽；`packs/demo`（12 章清洗）与 `packs/split3d` 共用同一 `agentcore`，领域差异全在契约里。
- 「先理解任务再动手」有对应物：`task.py` 的任务单解析（`parse_natural` 是 LLM 三个窄接口之一，猜的部分标 `assumed`）。
- **「选哪个领域」现在就是任务单里的声明字段，不是内核猜的**：`task.py:112` `pack=(pack.name if pack else obj.get("pack"))`。这个直觉在现有契约里已落地一半。

**要修正的三处**：
1. **分类不能让 Agent 自主拍板**。「这是手办还是机器人」没有函数能验证对错，按 §12 判据归技能 / 人，不归自主决策；且类别本身连续（机器人手办、机娘、拼装模型落在两类之间）。正确形态：类型是**显式任务输入（用户声明）**；Agent 可提议候选，但分类候选无法被内核校验（对比 `llm.py` 纪律：候选在外生成、内核校验——分类恰恰是验不了的那类），提议必须经人确认，不确定就拒收。与「能力为空时正确产出是拒收」同一条纪律。
2. **不是一个类型一套拆分技能**。语义分割算法不分手办 / 机器人——它打的是部件标签；按类型不同的是部件词表（head / arm_l vs panel / joint）、验收标准、连接方式。应做**一个分割工具 + 每领域的契约与技能（词表 + 判据）**，否则同一套几何算法写两遍、改一处漏一处（两套文献清单只重合一篇即此病）。
3. **分类不是「基本能力」，是入口上的一个窄接口**。已建成的基本能力是四件：目标倒推顺序、按路线挑一步、独立重算、记账与改道。分类层未建；且 `split3d` 13 工具 12 校验器全桩——分类完了也是调桩，真跑第 1 步 `NOT_IMPLEMENTED`。

**缺少的**：
- 分类之后的质量闭环（每件水密 / 壁厚、件间连接、装配干涉）不分手办 / 机器人，都要做；分类对只是入口对（SNAP3D：只分件 0% 稳定，加连接 + 仿真 95%）。
- 失败路径：类型不确定 → 拒收 / 问人；不在已知列表 → 拒收并说明或走通用路线；用户声明与模型提议冲突 → 人声明优先并留痕。不许默认猜。
- 任务不止类型一维：同一手办「展示整体」与「打印分件」拆法不同；任务输入至少 = 类型（声明）+ 目标 + 约束（`const` 已有 `pin_diameter_mm` / `min_wall_mm` 等）。
- 判定标准仍空白：手办「拆对」的标准谁定 → 技能 / 人；19 仓目前没有分件判定标准，这比分类层更靠前——没有判据，分类对了也无法验收。
- 分类依据要留痕进 `run.json` / 报告，复用已有决策日志，不做黑箱分类器。

### 一条正面结论

`segment_semantic` 只要 `produces` 与 `params` 不变，换实现不用改内核——这正是 18 仓契约设计的价值。
所以**先跑开源 baseline 不是返工、不是浪费**，后面换自己的方法只换 `impl`。

## 四、贯穿全程的约束

- 每步留痕、独立重算、不信自称；工具自称完成不算，校验器从磁盘重算。
- **归属按片段判**：真值比对 → 工具/校验器；「这套边界算不算对」「79% 够不够用」「无真值是否拒收」→ 技能/人。判据按片段用，不按整段用（`PACK-SPEC.md` §12.1）。
- **错误记忆贯穿全程**：每次失败落成带病因字段 + 适用条件的条目；命中只做「提前警示 / 拒收」，不得盖过人给的 `priority`；被独立校验器证伪即作废。「算不算同一个错」「该不该采信」留在技能 / 人。
- 技能侧判定标准变化同步进 19 仓并跑 `check_terms.py`；工具侧改动不改 18 仓判定逻辑。
- 契约或场景变化后重跑 20 仓 `build.py`，桌面工作台与产物主副本保持 sha256 一致。
- **验证分只读与写入**：只改口径 / 文档时用只读三件套（`doctor demo`、`doctor split3d`、19 仓 `check_terms.py`）；`accept.py` 会 `shutil.rmtree` 重建 `runs_accept/*`，而 20 仓 `build.py` 读这些 `events.jsonl` 生成 HTML 并复制桌面副本——契约或代码真改动后重跑验收时，必须同步重跑 `build.py` 并核对桌面与主副本 sha256 一致。
- **资产库**：以上任何产物同步到 Drive 前，必须先给用户过目清单并获明确确认；同名文件要说明冲突，不擅自覆盖。

**流程读法**：
1. **类型路由（§二.8）在阶段 3 之后才真正被使用**——第一个领域包的词表来自真值集本身的 11 / 37 类；`model_kind` 通道在阶段 1 先建好，手办 / 机器人两套词表与判定标准是阶段 2~3 之间按需补。
