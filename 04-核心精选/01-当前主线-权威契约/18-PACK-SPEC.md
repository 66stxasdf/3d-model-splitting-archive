# 领域包接口说明（PACK-SPEC）

这份文档是给**写工具的人**看的。你负责能力，内核负责编排。两边只通过下面这几个数据结构打交道，别的一概不用管。

先记住一句话：**内核不认识你的领域。** 它不知道什么是网格、什么是割线、什么是定位销。它只知道「有一组事实、有的工具能产出这些事实、产出之前需要别的事实」。所以你要做的全部工作，就是把这些关系声明清楚，然后实现函数。

---

## 一、一个包长什么样

```
packs/<包名>/
  manifest.json      事实 + 工具契约 + 校验器绑定 + 目标组 + 常量
  任意名字.py         实现（也可以指向任何已安装的模块）
```

最小可运行例子见 `packs/demo/`（纯文本分块，秒级跑完，全部能力都有）；
待填的骨架见 `packs/split3d/`（分件领域，契约齐了、实现全是桩）。

---

## 二、事实（facts）

事实是**世界的状态单元**，也是目标和依赖的单位。一条事实代表「某件事已经成立，且有证据」。

```json
{
  "id": "parts_verified",
  "label": "独立复验通过",
  "group": "verify",
  "initial": false,
  "terminal": false,
  "desc": "面数、体积、水密、互穿、装回体积守恒逐项核对"
}
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | 是 | 小写下划线。出现在契约、日志、代码里 |
| `label` | 是 | 中文名。报告里给人看的就是它，别写成 `fact_03` |
| `group` | 否 | 分组标签，只用于阅读和统计 |
| `initial` | 否 | 允许任务单直接声明「这个我已经有了」。**谨慎开**，开了就等于允许跳过产出与校验 |
| `terminal` | 否 | 属于最终产出，置位后不应被撤销 |
| `domain` | 否 | **按实例展开**声明。写了它，这条事实就不是「做没做」，而是「N 个实例各做没做」。见下 |

### 2.1 两种事实：一次达成 vs. 每个实例各达成一次

这是这一版最重要的一处区分，写契约前必须先想清楚：

| | 一次达成 | 每个实例各达成一次 |
|---|---|---|
| 写法 | 不写 `domain` | 写 `domain` |
| 例子 | `parts_available`（零件清单已分出） | `part_clean`（每一件各自清理完） |
| 内部状态 | `facts` 里存 `part_clean` | `facts` 里存 `part_clean@head`、`part_clean@arm_l`… |
| 「做完了吗」 | 事实在集合里就是完成 | **清单里每一个实例都在集合里**才算完成 |

```json
{
  "id": "part_clean",
  "label": "单件碎块已清理",
  "group": "core",
  "domain": {"from": "part_ids", "key": "part"},
  "desc": "每一件各自清理薄碎片、封口"
}
```

- `from`：`world.values` 里**实例清单**的键名。上游工具（这里是产出 `parts_available` 的那个）必须把这个列表写进 `values`，例如 `part_ids: ["head", "arm_l", "bag"]`。清单要等上游真跑了才有——在那之前内核如实说「不知道有几件」，既不判完成也不判失败。
- `key`：执行时内核注入给工具的**参数名**。工具从 `inp["params"]["part"]` 拿到自己该处理哪一件。名字自己定，但必须和工具里读的一致。

三条硬规矩：

1. **`domain.from` 指向的清单，必须有工具的 `writes` 声明会产出它。** 否则清单永远为空，而表现只是「规划器说不知道有几件」——doctor 会直接把这条报错，别等运行时才发现。
2. **`initial` 和 `domain` 不能同时写。** 任务单给的是一句整体声明，对应不上「每个实例各一次」，强行允许只会产生歧义。
3. **域是挂在事实上的，不是挂在工具上的。** 同一个事实可能被两个工具产出（语义分件 / 人工割线都产 `parts_available` 的下游）；域写在工具上，两个产出者就能写出两种量词，「算不算达成」就没有唯一答案了。

写事实时的四条经验：

1. **一条事实只回答一个是非问题。** `parts_available`（分出来了）和 `part_clean`（碎块清理了）必须分开，粒度太粗会让「出了什么错」无法定位。
2. **一次产出 N 个东西 ≠ N 次各产出一个。** 前者是不带 `domain` 的一次性事实（产出清单），后者才是按实例事实。分件里「分出清单」和「逐件清理」就是这两种，混在一起就分不清「做了 1 件」和「全做完了」。
3. **标签要用人的说法。** 「单件碎块已清理」比 `CLEANED` 好，因为报告的第一读者是干活的人。
4. **不要为了"看起来完整"造事实。** 没工具产出、也不允许初始给出的事实，会让规划器一直报不可达（doctor 会提示）。

## 三、工具契约（tools）

```json
{
  "name": "cut_plane",
  "title": "平面半空间切",
  "produces": "parts_cut",
  "requires": ["route_known", "lod_ready"],
  "when": "branch == 'plane'",
  "needs_fields": ["inputs.model"],
  "params": {"lod": "$value.lod_path", "out_dir": "$run_dir/cut"},
  "verify": "my_verify:parts_cut",
  "impl": {"type": "python", "ref": "my_tools:cut_plane", "timeout_s": 900},
  "on_fail": "fallback",
  "fallback": [],
  "writes": ["parts_dir"],
  "cost_s": 90,
  "priority": 10,
  "admission": false,
  "desc": "平面缝用半空间盒布尔，最快也最稳"
}
```

按实例工具的契约长这样（注意 `params` 里**不写**实例参数，它由内核注入）：

```json
{
  "name": "clean_part",
  "title": "单件清理",
  "produces": "part_clean",
  "requires": ["parts_available"],
  "params": {},
  "impl": {"type": "python", "ref": "my_tools:clean_part", "timeout_s": 900},
  "on_fail": "skip_instance",
  "cost_s": 30
}
```

`part_clean` 在 manifest 里带 `domain`，所以内核会按清单把它展开成 N 次调用，
每次把 `part` 注入 `params`。工具一次只处理一件，**不要在工具里 `for` 全做完**——
那样内核看到的还是「一步」，件账、单件失败、断点续跑全都会失效。

### 3.1 `produces` 只能有一个

一个工具只产出一个事实。产两个说明该拆成两个工具。

原因很实际：只要一个工具能产出两个事实，规划器就无法判断「只缺其中一个」时该不该跑它，回退也会变成掷骰子。

### 3.2 `requires` 是硬依赖

列在这里的事实必须已经成立，否则这个工具不会被选中。规划器就是靠它反向展开出整条链的。

**`params` 里读了谁的值，就要把谁的事实列进来。** 内核会静态检查：
参数引用 `$value.K` 时，声明会写 `K` 的那个工具所产出的事实，必须在本工具
`requires` 的传递闭包里。漏了就是**隐式依赖**，`doctor` 直接判死，不让它跑到运行时。

```jsonc
// 错：读了 $value.lod_path（由 prep_lod 在产出 lod_ready 时写入），却只声明 input_ok
{"name": "segment_semantic", "requires": ["input_ok"],
 "params": {"src": "$value.lod_path"}}

// 对：把写入者产出的事实列进 requires
{"name": "segment_semantic", "requires": ["input_ok", "lod_ready"],
 "params": {"src": "$value.lod_path"}}
```

为什么要这么硬：漏声明在**整链跑**时可能看不出来——规划器碰巧因为别的路线
先排了 `prep_lod`，值恰好存在。但单独跑这一步就会 `MISSING_PARAM`，
报错看起来像「分割器没装好 / 环境问题」，排查方向被完全带偏。
这种「碰巧能跑」比稳定失败更危险。

这条判定属于内核，不写进技能。技能只能裁定「这份标签能不能采信」，
不能负责「上游事实是否已就绪」——后者有客观答案，交给提示词自觉是不可靠的。

### 3.3 `when` 是适用条件（mini DSL）

条件必须是**数据**，不能是代码。语法只有这些：

```
比较      ==  !=  >  <  >=  <=
成员      in     not in
布尔      and    or    not
括号      ( )
字面量    'text'   123   4.5   true   false   null   ['a','b']
取值      values.mode        （世界里的值）
          task.inputs.mode   （任务单输入）
          mode               （世界值的简写，同名时请用 values.mode 消歧）
```

不支持函数调用、算术、属性方法。这不是偷懒——条件要能被静态检查、能被非 Python 的运行器解释、能被 diff 审阅。

**条件里引用的值，必须由上游工具写进 `values`。** 否则运行期求值会失败（内核会把它当作「该工具不可选」，并在报告里写明原因）。

### 3.4 `needs_fields` 检查任务单

点路径写法，如 `inputs.model`。缺了就不选这个工具，报告里会说「任务单未提供」。

它和 `requires` 的分工：`requires` 管「前置产物」，`needs_fields` 管「用户得给我什么」。

### 3.5 `params` 是参数来源声明

**不允许在契约里藏字面量。** 每个参数都写清从哪来：

| 写法 | 含义 |
|---|---|
| `$input.model` | 任务单 `inputs` 里的字段（缺失即硬错） |
| `$value.lod_path` | 世界里的值（由上游工具写入） |
| `$const.pin_diameter_mm` | 包常量（`manifest.json` 的 `const`） |
| `$run_dir/cut` | 本次运行目录下拼接 |
| `$workspace` | 工作区 |
| `$artifact.cut_part_A` | 按 role 找上游产物路径 |
| `$env.SOME_VAR` | 环境变量 |
| `${task.tag}-x.json` | 字符串模板内插 |

推荐的做法是：**路径类参数用 `params`，上游产物路径从 `inp["world"]["values"]` 里读。**
后者看起来"不够声明式"，但它在预览期不会误报缺参数，而且依赖关系已经由 `requires` 表达清楚了。

### 3.6 `verify` 绑校验器（**必填，否则内核拒绝运行**）

见第五节。这一条是硬要求：没有校验器的事实，内核不允许任何工具产出它。

### 3.7 `impl` 实现

```json
{"type": "python", "ref": "模块:函数", "timeout_s": 300}
{"type": "cmd", "argv": ["blender", "-b", "--python", "my.py",
                        "--in", "{request}", "--out", "{result}"], "timeout_s": 900}
```

- `python`：进程内调用。快，但**超时无法真正杀掉线程**，报告里会如实标注。
- `cmd`：子进程 + JSON 文件交换。任何语言都能接。`{request}` `{result}` `{run_dir}` `{workspace}` 会被替换成实际路径。**这是给 Blender 这类重工具用的正道**，超时会被真正结束。

`python` 实现如果放在包目录里，会自动按文件路径加载，不需要 pip install；包内模块之间可以互相 import。

### 3.8 `on_fail` 失败策略（必须预先想好）

| 值 | 行为 | 什么时候用 |
|---|---|---|
| `abort` | 停下，结局 FAILED | 大多数情况。**宁可停，不要瞎猜** |
| `retry` | 重试 `max_retry` 次 | 只对 `TIMEOUT` / `TOOL_ERROR` / `PY_EXCEPTION` 这类环境抖动生效 |
| `fallback` | 停用本工具，让规划器重新找路 | 有真正等价的备选时 |
| `skip_instance` | 只放弃当前这一件，其余实例继续 | **按实例工具专用**，且只在该件坏了不该拖累整批时用 |

`skip_instance` 的四条语义，写之前请确认你接受：

1. **只能用在带 `domain` 的事实上。** 一次性事实写它是把「整件事失败」悄悄降级成「跳过」，doctor 会报错。
2. **放弃 ≠ 成功。** 这一件会单独记进 `abandoned`，目标仍然判不达成，最终结局不是 SUCCESS。
3. **放弃会沿依赖链传播。** 某件清洗失败，它的复核、导出也一并标为放弃；否则下游会一直等一个永远不会来的实例，最后报「走不通」，把排查方向带偏。
4. **`ready` 与 `satisfied` 分开。** 作为前置，已放弃的那一件不阻塞其余件开工；作为目标，它仍算没做完。两者合成一个必然两头错。

用 `fallback` 前请确认：**回退目标的适用条件与被回退工具不是互斥的。**
比如 `cut_fixed` 的条件是 `mode == 'fixed'`，回退目标 `cut_adaptive` 要求 `mode == 'adaptive'`，
这条回退永远走不通。doctor 会对此报警告。

### 3.9 `admission` 准入类工具

标了 `admission: true` 的工具失败时，结局是 **REJECTED（主动不干）**，不是 FAILED（干坏了）。

这个区分很重要：没开始切不叫切失败。混在一起，报告会把「你的数据不合格」写成「系统坏了」，方向就错了。

适合标 admission 的：入厂质检、割线校验、分块合格性检查——**判「该不该做」的那种**。

### 3.10 `writes` 声明会写进 `world.values` 的键

```json
"writes": ["part_ids", "parts_dir"]
```

**每个往 `world.values` 里写值的工具都要声明它写了哪些键**（写进 `values` 或 `values_global` 的都算）。
两个用途：

- **静态检查实例清单。** 某条事实写了 `domain: {"from": "part_ids"}`，却没人声明会产出 `part_ids`，
  那清单永远是空的、按实例展开永远不开始。doctor 会在交付前直接报错，而不是让你跑到一半去猜。
- **静态检查 `$value` 的来源。** 参数引用了 `$value.K` 却没人声明会写 `K`，运行时必然取不到值；
  有人写了但产出的事实不在依赖链上，就是隐式依赖（见 3.2）。两种都在 doctor 阶段判死。
- **让人一眼看清谁提供什么。** 契约是数据，读 manifest 就该能画出数据流。

注意：`writes` 声明的是**键名**，不是作用域。按实例工具的 `values` 会落进实例私有作用域（见 4.4），
`values_global` 才落进全局；两者都该在 `writes` 里报备。

早期内核把「params 里被读到的 `$value.K`」也算进「有人会写」的集合，等于**有人读就算有人写**，
上面两条检查因此全部失效。现在只认 `writes`，别再靠「运行时大概会有」来兜。

### 3.11 `cost_s` / `priority`：priority 定路线，cost 定先后

`cost_s` 要写真实开销。写小了会在同等条件下被优先选中，进而误判。

**当多个工具都能产出同一个事实时，`priority` 决定走哪条路线，不是决定谁先跑。**
规划器先按 priority 从高到低挑一条通往目标的路线，再沿这条路往前找第一个能执行的动作。

这点很关键。纯贪心（只看「此刻谁离目标近、谁能马上跑」）会系统性地偏向当场就能跑的那条：

<!-- CONTRACT-SNAPSHOT: split3d -->
```json
[
  { "name": "cut_plane",        "produces": "parts_available", "priority": 20,
    "requires": ["route_known", "lod_ready"] },
  { "name": "segment_semantic", "produces": "parts_available", "priority": 10,
    "requires": ["input_ok", "lod_ready"],
    "needs_fields": ["inputs.model_kind"] }
]
```
<!-- CONTRACT-SNAPSHOT-END -->

上面这段是**契约副本**，不是随手写的示意：它带 `CONTRACT-SNAPSHOT` 标记，
验收 T26 会把它与 `manifest.json` 逐字段对账。改契约时这两处必须一起改，否则验收会 FAIL。
（3.2 节里那个 `// 错：` 的片段是**故意写错的反例**，不带标记，不参与对账。）

`cut_plane` 要先降面、读割线、定分支才能跑；`segment_semantic` 当场就能跑。
若按贪心，人明明画了割线，系统也会自作主张去认语义——把人的决定让位给了算法偏好。
给 `cut_plane` 更高 priority，规划器才会先认这条路，再回头把 `prep_lod → seam_ingest → route_branch`
这些前置一步步补上。**给不给割线，路径自己切换，不需要改代码。**

`needs_fields` 是**输入门**：声明了 `inputs.model_kind`，任务单没给这个字段时
`segment_semantic` 直接不可达（不是跑起来再报错）。类型声明的规矩见 §二.8：
人声明优先、模型提议需人确认、不确定就拒收——所以没有 `model_kind` 时
`goal=parts` 会在 0 步诊断成 `NEED_INPUT`，由 T27 守着。

## 四、工具的实现长什么样

### 4.1 输入 `inp`（内核构造，只读副本）

```python
{
  "tool":      "clean_part",     # 当前工具名
  "instance":  "head",           # 按实例工具才有；一次性工具是 None
  "params":    { "part": "head", ... },  # 已解析 + 实例参数已注入
  "task": {
    "task_id": "...", "tag": "...",
    "goals": [...], "inputs": {...}, "constraints": {...}
  },
  "world": {
    "facts":  ["input_ok", ...],   # 已排序
    "values": { ... },             # 已合并当前实例私有值（见 4.4）
    "instance": "head",            # 同顶层，方便从 world 一处取
    "done_instances": ["arm_l"]    # 同一事实下已完成的其它实例
  },
  "artifacts": { "role": {"path":..., "bytes":..., "sha256":...} },
  "run_dir":   "D:/.../runs/20261110-203742-e3c0",
  "workspace": "D:/.../runs/20261110-203742-e3c0/work",
  "step":      7
}
```

**按实例工具的实例参数从哪来：** 契约 `domain.key`（这里是 `part`）由内核在参数解析之后、
指纹计算之前注入 `params`。所以 `params` 里不要写死它，直接读 `inp["params"]["part"]`。
注入位置必须在指纹之前——6 个零件用同一工具、同样的契约参数，唯一区别就是实例；
若指纹在注入前算，6 次动作会同指纹，第 2 件就被防环当成绕圈拦死。

工具拿不到内核对象，也改不到 Agent 的状态。**这条如果破了，编排就不再受控**——工具可以自己宣布成功，Agent 就成了摆设。

### 4.2 输出（普通 dict）

```python
return {
    "ok": True,
    "facts": ["parts_cut"],          # 只能写自己的 produces，写别人的会被判 FACT_OUT_OF_SCOPE
    "values": {"cut_dir": "...",     # 小摘要：路径、面数、体积、指纹
               "parts_n": 2},
    "values_global": {"...": ...},  # 可选：跨实例共享的值，见 4.4
    "evidence": {"faces": 194408, "volume_mm3": 12345.6},  # 进账本，供人复查
    "artifacts": [                   # 必须真在磁盘上，校验器会去 stat
        {"role": "cut_part_A", "path": "D:/.../part_A.stl", "bytes": 123456}
    ],
    "metrics": {"parts": 2},
    "warnings": ["目标 2 份但只有 1 块，按块数切"],
    "message": "均分为 2 份，共 1461 字符"
}
```

按实例工具的 `artifacts` 不用自己加实例后缀：内核会把 `role` 改成 `role@实例`，
否则 6 件交付物在产物清单里只剩最后 1 件。

失败时：

```python
return {"ok": False, "reason_code": "SEAM_NOT_CLOSED",
        "message": "首尾间隙 3.2mm，超过容差 0.1mm",
        "evidence": {"gap_mm": 3.2, "tol_mm": 0.1}}
```

### 4.3 七条纪律

1. **`values` 里只放小摘要。** 几何写文件，路径进 values。`run.json` 是给人读的，别塞网格。
2. **失败必须给 `reason_code`，而且要能归类。** `UNKNOWN_FAILURE` 会让回退决策失去依据。
3. **不要自己判断"我做完了"。** 返回 `ok=True` 只是"我认为我做了"，结论由校验器从磁盘重算。
4. **不吞异常。** 抛出来能被接住并归成 `PY_EXCEPTION`，但那条路信息少一半。
5. **时长和体积要真实。** 假的成本数字会污染规划。
6. **按实例工具一次只做一件。** 别在工具里 `for` 遍历整张清单。内核按件调度、按件记账、
   按件失败，工具里批处理等于把这些全绕过——报告会显示「跑了 1 步」而不是「12 件里 11 件做完」。
7. **按实例工具不要在返回值里塞全局汇总。** 想让下游一次性工具看见的值，走 `values_global`（见 4.4）。

`NotImplementedError` 有特殊含义：它表示**能力尚未提供**，结局是 `UNDECIDABLE`（不是 FAILED）。骨架包就靠这个机制如实报「这活还没人干」。

### 4.4 两个值域：实例私有 vs. 全局共享

按实例工具最常踩的坑是：**6 个零件都往 `values` 写 `part_path`，最后只剩 `hair.stl`，前 5 个路径静默丢失。**
内核用作用域解决它，但你要知道值落在哪：

| 写在返回里的键 | 落到哪 | 谁看得见 |
|---|---|---|
| `values`（按实例工具） | `world.values["@实例"]`，私有 | 同一实例的后续工具 + 校验器 |
| `values`（一次性工具） | `world.values`，全局 | 所有工具 |
| `values_global`（任何工具） | `world.values`，全局 | 所有工具 |

- **工具读 `world["values"]` 时，内核已经把当前实例的私有值合并进去了**（实例优先于全局），
  所以照常写 `_wv(inp, "clean_path")` 就行，不必知道作用域存在。
- **要让下游一次性工具读到，必须写 `values_global`。** 典型场景：`clean_part` 逐件把清洗产物
  写进同一个目录，这个目录路径得用 `values_global={"clean_dir": ...}` 告诉 `find_contacts`；
  写进 `values` 只会落到 `@head` 里，下游从全局视图读不到，报出来是「参数取不到」——
  看起来像缺输入，其实是值被丢了。
- 每条实例写入都会落进 `run.json` 的 `scoped` 段，事后可查，不是黑箱。

`values_global` 必须是 dict；写成别的类型会被内核当成没给（防工具写错形状把编排带崩）。

## 五、校验器（verifier）

每个事实都必须有校验器。内核在工具返回后**独立调用**它，工具说什么不算。

```python
def parts_cut(payload) -> {"ok": bool, "why": str, "detail": dict}
```

`payload` 里有：

```python
{
  "fact":      "parts_cut",
  "instance":  None,                   # 按实例校验时是当前实例，如 "head"
  "declared":  ["parts_cut"],          # 工具声称产出的
  "values":    {...},                  # 本次工具返回的 values
  "world": {"facts": [...], "values": {...}, "instance": ..., "done_instances": [...]},
  "artifacts": [...],
  "evidence":  {...},
  "metrics":   {...},
  "const":     {...},                  # 包常量，阈值都在这里
  "run_dir": ..., "workspace": ..., "task": {...}
}
```

判定某个条件时请用 `world.values + values`（后者覆盖前者）。
只看 `values`，就变成让工具自己给答案对答案了。
`world["values"]` 同样已合并当前实例私有值。

**按实例的校验器必须认 `payload["instance"]`。** 只判「清洗产物存在」是不够的——
12 件里第 5 件坏了，产物文件照样在盘上，不认实例就会把坏件也放过去。
正确做法：用 `instance` 拼出该件的路径，从磁盘独立重算这一件；认不出实例就直接判失败。
清单类事实（如 `chapters_listed`）的校验器则相反：**别信工具报的清单，去数磁盘上的文件**。

### 写校验器容易犯的四个错

1. **拿工具报的值去校验工具报的值。** 工说"体积 100"，校验器读到 100 就通过——这不是校验，这是复述别人的话。
   正确做法：从产物文件重算体积，再和 values 里的比。
2. **用文本模式读文件。** Windows 上 `\r\n → \n` 的转换会让两侧算出的字节数差几十，守恒式永远对不平。**一律按字节读**；
   写侧也一样（`open(path, "wb")`），读写口径只要有一侧做换行转换，守恒式就永远对不平。
3. **把"没算出来"当"通过"。** 校验器抛异常时内核会判 `VERIFY_ERROR` 并停止，这是对的。千万别 `try/except` 之后返回 `ok=True`。
4. **不认实例。** 按实例事实的校验器忽略 `payload["instance"]`，等于只验了「有一件合格」，
   坏件换到哪一章都照样通过（T18 就是拿"字符数对、内容被改了一个字"抓这个）。

## 六、目标组

```json
"goals": {
  "inspect": ["input_ok"],
  "cut":     ["parts_verified"],
  "deliver": ["exported"]
}
```

任务单可以直接写组名，也可以写事实名，还可以混着写。

**不要在这里写步骤。** 顺序是推出来的，写步骤就把 Agent 降级成执行器。

**按实例的事实也能直接当目标**（`"book": ["chapter_exported"]`）。此时内部是三态判定：

| 状态 | 含义 | 内核怎么做 |
|---|---|---|
| `True` | 清单里每一件都完成 | 判成功 |
| `False` | 清单空 / 少几件 / 有放弃的 | 继续做或如实报未达成 |
| `None` | 清单还没产生 | **继续做**，绝不判成功 |

第三态是刻意留的：「有几个零件」要等分割跑完才知道。把它压成布尔，无论压成哪边
都会产生一个专门的假象——压成 `True` 就是一件没做先报成功，压成 `False` 就是误判不可达。
预算耗尽时内核会用符号推演算出还差多少步，并在报告里给出 `budget.max_steps` 建议值，
而不是只丢一句「步数用满」。

## 七、常量

```json
"const": {
  "pin_diameter_mm": 3.0,
  "radial_clearance_mm": 0.2,
  "min_wall_mm": 0.8
}
```

阈值、间隙、口径这类数字一律放这里。散落在实现代码里的常量，改的时候一定会漏一处。

工具用 `params` 里的 `$const.xxx` 取；校验器从 `payload["const"]` 取。

## 八、交付前必做

```bash
python -m agentcore doctor <包名>          # 契约自检（L1 结构 / L2 语义 / L3 实物）
python -m agentcore doctor <包名> --shallow # 只查结构，不导入实现
python -m agentcore tools <包名>           # 看清依赖图
python -m agentcore plan <包名> --input k=v --goal <目标组>   # 只推演，1 秒
```

`doctor` 报错就是**契约写错了**（不是你的实现有问题），报「桩」就是**活还没干**。
两种都必须在交付前清掉。

用了 `domain` 的包，doctor 还会多查两件事：`from` 指向的实例清单有没有工具的 `writes`
声明会产出、`skip_instance` 是不是用在按实例事实上。这两条以前只能等运行时才发现，
而且表现是「规划器说不知道有几件」，不看代码根本猜不到是契约漏了。

打桩期间跑 `run` 会得到 `UNDECIDABLE + NOT_IMPLEMENTED`，这是正确行为——它说的是「能力未提供」，不是「你的数据有问题」。

## 九、常见错误对照表

| doctor 说 | 通常是什么 |
|---|---|
| `工具 X 产出未登记的事实` | manifest 里少了这条 fact，或 id 拼错了 |
| `事实 X 没有任何校验器` | 漏了 `verify` 字段或 `verifiers` 里的绑定 |
| `工具依赖成环` | requires 互相指向，检查谁应该是上游 |
| `工具 X 的参数 Y 来源 unknown 未知` | 参数写法只支持 `$input` / `$value` / `$const` / `$run_dir` / `$artifact` / `$env` |
| `工具 X 的回退目标 Y 带不同条件` | 这条回退大概率走不通，换条件相同的备选 |
| `工具 X 的实现加载失败` | 模块名或函数名不对；或者文件不在包目录里且没安装 |
| `工具 X 的实现不接受参数` | 签名应为 `def fn(inp)` |
| `事实 X 没有任何工具能产出` | 目标要求的链路中间断了 |
| `事实 X 的实例清单来自 Y，但没有任何工具的 writes 声明会产出它` | 上游漏写 `Y`，或漏了 `writes` 声明——清单会永远是空的 |
| `事实 X 既是 initial 又带 domain` | 初始事实是整体声明，没法按实例对应，去掉其中一个 |
| `工具 X 用了 skip_instance，但它产出的事实不是按实例的` | 给该事实加 `domain`，或把失败策略改回 `abort` |
| `按实例的事实必须指定是哪一个实例` | 代码里调了 `world.add(fact)` 却没带实例；工具返回永远不该触发这个 |
| 目标显示「无法判定：实例清单还没有」 | 正常，不是错误。清单要等上游跑完才有，内核会继续做 |
| 报告里某件是「弃」，下游也是「弃」 | 放弃沿依赖链传播了，这是对的；结局仍不会判成功 |
| `参数引用 $value.K，但没有任何工具的 writes 声明会写入它` | 上游漏写 `values` / `values_global`，或漏了 `writes` 报备 |
| `这是隐式依赖……请把对应事实补进 requires` | 读了上游的值却没声明依赖它；整链跑可能碰巧不报错，单独跑必 `MISSING_PARAM` |
| T26 报「PACK-SPEC 契约快照与 manifest 不一致」 | 接口书 3.11 的示例是契约副本，改 manifest 时忘了同步它；两者一起改 |
| `MISSING_PARAM` / `NEED_INPUT` | **不等于环境坏了**。可能是任务单漏传 `$input.*`（内核覆盖不到，T25 只查 `$value.*`），也可能是上游没写值；见 12.1 |
| 状态显示「桩」 | 实现还没写 |

## 十、能不管的事

这些内核都替你处理了，写工具时不用操心：

- 顺序：从目标反向展开算出来的；多入口时按 priority 定路线
- 前置检查：requires 与 needs_fields 自动判；按实例前置用 `ready` 口径
- 按实例展开：清单出来后自动拆成 N 次，实例参数自动注入 `params`
- 实例作用域：按实例 `values` 自动隔离，不会互相覆盖；`values_global` 走全局
- 失败重试与改道：按 on_fail 的策略执行；`skip_instance` 自动级联放弃下游
- 防死循环：同一工具 + 同一参数 + **同一实例** 只做一次
- 预算：步数和墙钟都有上限；用完会算出还差多少步并给建议值
- 断点续跑：世界状态落盘（含 `fact@实例` 与实例私有值），重启不重做
- 留痕：每一步的「为什么选它」和「为什么没选别的」都进报告
- 件账：按实例统计矩阵，一眼看出「12 件里 11 件做完」，而不是「跑了 36 步」
- 结论文案：报告首段由结局决定，不由产物数量决定

| 我要… | 写在哪 | 长什么样 |

## 十二、什么进工具、什么进技能、什么两边都不进

**一条可操作的判据：**

> 能被一个函数判定成败 → 工具。
> 只能由人定判定标准 → 技能。
> 两样都不成立 → 不要写进任何一边。

`segment_semantic` 是最容易判错的一个，把它拆开就清楚了：

| 片段 | 归属 | 理由 |
|---|---|---|
| 跑模型、输出逐面片标签 | **工具** | 能执行，有执行语义 |
| 「头认对了吗」 | **两边都不写** | 没有任何函数能独立判定；写进校验器会变成 L8 那条已被证伪的路 |
| `cost_s: 300` / `timeout_s: 900` / `priority` / `on_fail` | **工具** | 技能里不会写这些字段 |
| 「79% 意味着约 1/5 边界是错的」 | **技能** | 判定标准，不是计算 |
| 该走 A（前馈模型）还是 B（人工关键点） | **技能** | 有无 GPU 是环境事实，不是计算结果 |
| 这份标签能不能进切割 | **技能** | 没有客观验收函数，只有判定标准 |
| `SEGMENTATION_EMPTY` 是「没分出来」还是「模型不可拆」 | **技能** | 数值一样，结论相反，只能由人裁定 |

契约里因此**没有**「部位正确性」这类事实或校验器。`part_verified` 只查
水密、自交、体积、壁厚——一块从膝盖上切下来的件同样全部通过。
**校验器能证明它是零件，不能证明它是那个部位。**

所以在能力还是桩的时候，技能在这条链上的正确产出是**拒收**，不是识别：

- 缺 GPU → 退回「人工点 6~8 个关键点 + 测地距离」的待办，把活交回人
- 有人给了 semantic 标签 → 要求人工确认边界后才准入
- 有人拿 mIoU 79 证明可用 → 先判输入是否同分布（PartNeXt 上只有 50.22），否则整个分区记 `UNKNOWN`
- 三种都没有 → 报告写「语义分区不可用」，**不许降级成包围盒硬分**

一句话：**技能能拦住错误的做法，但产不出正确的结果。**
把识别写进技能，等于逼 Agent 用别的方式伪造一个产出——那是最坏的结果。
反过来，把「上游事实是否就绪」写进技能也一样错：它能被静态判定，归内核（见 3.2）。
**但这条只适用于 `$value` 通道，且只删该删的那一片段——见 12.1。**

### 12.1 判据按「片段」用，不按「整段」用；静态检查有明确的通道边界

**上面那句「能被静态判定 → 归内核」是有覆盖面的，不能整段套用。**

内核的隐式依赖检查（3.2）只检查 `$value.*`：写入者、产出事实、`requires` 传递闭包
三者能否对上，全是契约里的静态数据。「上游就绪」因此能被判死。

但 `_PARAM_SRC` 有 9 类来源，其中 `input` / `task` / `env` 是**运行时任务单与环境字段**。
契约能声明「这一步需要 `inputs.seam`」（`needs_fields`），却无法保证运行时真的传了。
`contract.py` 里那句 `if head != "value": continue` 就是这条边界——
`--input seam=` 漏传、字段值为空、条件分支临时引用，仍会真实地抛 `MISSING_PARAM`。

于是同一段技能里，三件事的归属是不同的：

| 片段 | 归属 | 理由 |
|---|---|---|
| `$value` 上游是否就绪 | **内核** | 契约静态可判，doctor 判死（3.2 / T25） |
| 漏传时 `MISSING_PARAM` **该读成什么** | **技能** | 没有函数能判「这是环境坏了还是参数没给」，只有判定标准 |
| 曾漏过 `lod_ready` 这件事 | **技能（历史注）** | 防止后人照旧契约重犯，不是判定逻辑 |

**「删掉自查纪律」≠「删掉整段」。** 把第二、三行一起删掉，Agent 下次拿到
`MISSING_PARAM` 仍会去重装分割器——只是这次没有文字拦住它了。

实测口径（写技能时说准，别夸大）：漏传 `$input.model` 时内核给的是
**0 步 `UNDECIDABLE / NEED_INPUT`**，reasons 会点名缺哪个字段；但**步骤级 reason 仍是
`MISSING_PARAM`**，且同一个顶层码同时覆盖「用户没传」和「上游 `$value` 没写」两种成因。
所以技能该写的不是「内核会把它误报成环境错误」，而是**「这个码不等于环境坏了，
先分是任务单没给还是上游没写」**——区分这两种成因需要判断上游事实本该不该成立，
这是裁定，不是计算。

> 一条可以双向使用的记法（来自技能侧，已核对）：
> **技能里每出现一条「你先自己检查 X」，都要问 X 能不能被函数判定。
> 能判的搬回内核，判不了的才留在技能。**
> 反方向同样成立：内核补了静态检查，技能里对应的自查要删；
> 但内核没覆盖到的通道，技能里的裁定要留。
